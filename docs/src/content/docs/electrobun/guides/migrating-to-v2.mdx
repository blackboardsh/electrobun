description: "Move an Electrobun 1.x project to the 2.x Hutch and Cottontail toolchain."
---

Electrobun 2.x separates build tooling from the JavaScript runtime. Hutch
replaces Bun, npm, and the old Electrobun CLI for Electrobun project workflows.
It owns package management, scripts, builds, native toolchains, and
distribution, and uses Cottontail to execute JavaScript and TypeScript lifecycle
scripts.

Cottontail is the default JavaScript main-process runtime bundled into finished
applications. It provides Node.js and Bun compatibility where Electrobun apps
and their packages need it, so existing TypeScript main processes should
usually run without source changes.

## 1. Install Hutch

macOS or Linux:

```bash
curl -fsSL https://hutch.blackboard.sh/hutch/install.sh | sh
```

Windows PowerShell:

```powershell
& ([scriptblock]::Create((irm https://hutch.blackboard.sh/hutch/install.ps1)))
```

Restart the terminal if the installer added `~/.dash/bin` to your shell path.

For a new project, run the interactive template chooser:

```bash
hutch electrobun init
```

Existing `npx electrobun init` and `bunx electrobun init` entry points remain
available. The npm package now installs the appropriate Hutch channel when it
is missing and delegates to the same template chooser instead of carrying a
second CLI implementation.

## 2. Keep Electrobun as a project dependency

The `electrobun` package still provides configuration types, browser code,
preloads, and SDK source. Install it through Hutch:

```bash
hutch install
```

Existing `bun.lock` files remain supported. Commit the lockfile as before.

## 3. Replace build commands

Typical command migrations are:

| Electrobun 1.x | Electrobun 2.x |
| --- | --- |
| `bun install` | `hutch install` |
| `bun run dev` | `hutch run dev` |
| `bunx electrobun dev` | `hutch electrobun dev` |
| `bunx electrobun build --env=canary` | `hutch electrobun build --env=canary` |
| `bunx electrobun build --env=stable` | `hutch electrobun build --env=production` |
| `bunx <package>` | `hutch x <package>` |

For example:

```json
{
  "scripts": {
    "dev": "hutch electrobun dev --watch",
    "build:canary": "hutch electrobun build --env=canary",
    "build": "hutch electrobun build --env=production"
  }
}
```

Hutch can vendor and build every supported main process: Cottontail, Bun, Zig,
Rust, Go, and Odin. A separate global installation of each native toolchain is
not required when Hutch has a pinned toolchain for the host.

## 4. Use the runtime-neutral SDK namespace

Change main-process imports from `electrobun/bun` to `electrobun/main`:

```ts
import { BrowserWindow } from "electrobun/main";

const win = new BrowserWindow({
  title: "My app",
  url: "views://mainview/index.html",
});

void win;
```

`electrobun/bun` and its focused subpaths remain supported as deprecated aliases
for incremental migration. The source directory can remain `src/bun`; the SDK
namespace does not determine the selected runtime.

## 5. Choose the main process

To move an existing TypeScript main process to Cottontail, change the config
block while keeping the entrypoint itself:

```ts
import type { ElectrobunConfig } from "electrobun";

export default {
  app: {
    name: "My App",
    identifier: "com.example.my-app",
    version: "2.0.0",
  },
  build: {
    mainProcess: "cottontail",
    cottontail: {
      entrypoint: "src/bun/index.ts",
    },
  },
} satisfies ElectrobunConfig;
```

To switch back to the actual Bun runtime, configure it explicitly:

```ts
import type { ElectrobunConfig } from "electrobun";

export default {
  app: {
    name: "My App",
    identifier: "com.example.my-app",
    version: "2.0.0",
  },
  build: {
    mainProcess: "bun",
    bun: {
      entrypoint: "src/bun/index.ts",
    },
  },
} satisfies ElectrobunConfig;
```

Hutch still performs package installation, builds, and packaging when Bun is
the selected application runtime.

## 6. Use the release channels

Hutch defaults to `dev`, `canary`, and `production` build environments. The
name `stable` continues to work as an alias for `production`, including
`--env=stable`, installer channel selection, and Hutch/Cottontail version
selectors. New scripts and CI configuration should use `production`.

Production application names are unsuffixed; canary application names include
`-canary`. Lifecycle hooks receive the canonical `ELECTROBUN_BUILD_ENV` value:
`dev`, `canary`, or `production`.

## 7. Review build automation

Hutch builds for the current host. Keep one native CI runner for every OS and
architecture you release. Review signing, notarization, artifact upload, and
update metadata configuration when replacing old `bunx electrobun` commands.

## 8. Test the migration

```bash
hutch install
hutch electrobun dev
hutch electrobun build --env=canary
hutch electrobun build --env=production
```

Verify application startup, RPC, webviews, updater metadata, signing, and any
native dependencies on macOS, Windows, and Linux.

<Aside type="note">
Electrobun 2.x also supports Zig, Rust, Go, and Odin main processes. Migrating
to a native main process is optional and should be treated as a separate change
after the 2.x toolchain migration is working.
</Aside>

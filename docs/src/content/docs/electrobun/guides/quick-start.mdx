This page takes you from nothing to a running desktop app. You'll install
Hutch — Electrobun's build and workspace CLI — scaffold a project from a
template, and run it. A couple of minutes, start to finish.

## Install Hutch

On macOS or Linux:

```bash
curl -fsSL https://hutch.blackboard.sh/hutch/install.sh | sh
```

On Windows PowerShell:

```powershell
& ([scriptblock]::Create((irm https://hutch.blackboard.sh/hutch/install.ps1)))
```

Restart the terminal if needed, then check that it's on your path:

```bash
hutch --version
```

That's the only Electrobun-specific global install you need. Hutch handles
scripts, builds, devkits, toolchains, and releases. A JavaScript project still
uses its chosen package manager for ordinary dependencies; a Rust or Go project
uses Cargo or Go modules. When a project needs a compiler, Hutch fetches its
exact configured version.

## Create a project

```bash
hutch electrobun init
```

This opens an interactive picker: arrow keys to browse templates, Enter to
choose. Hutch downloads the current stable template catalog and creates
the project. Templates range from a minimal hello-world to full app skeletons
with React, Solid, Vue, Svelte, or GPU-rendered UI — the picker is a nice way
to browse what exists.

Already know what you want? Skip the picker:

```bash
hutch electrobun init my-app --template=hello-world
```

Add `--beta` to scaffold from the latest **beta** templates instead of stable:

```bash
hutch electrobun init my-app --beta
```

:::note
`bunx electrobun init` and `npx electrobun init` work too. The npm package is a
thin bootstrap that installs/executes Hutch and forwards every argument. It
defaults to stable templates unless you pass `--beta`. Its npm version is
independent and never chooses the project's Electrobun product, SDK, runtime,
or template version.
:::

## Run the app

```bash
cd my-app
hutch run dev
```

A window should open on your desktop. That's your app.

`init` already ran the template's explicit `install` task after extraction and
devkit preparation. For the default JavaScript templates that task delegates
`ci` to npm; native-only templates do not define it. If you initialized with
`--skip-install` or `--offline`, run `hutch run install` before `dev` when the
selected template provides that task.

The `dev` task builds the app, launches it, and rebuilds when you edit source
files. Hutch resolves both tasks only from `hutch.config.ts`; the configured
external package manager still owns `package.json`, dependency resolution, and
its lockfile.

The template's `electrobun.config.ts` contains an exact product pin:

```ts
export default {
  electrobun: {
    version: "2.0.0",
  },
  // app and build configuration...
};
```

During `init`, Hutch syncs that exact core and SDK release into the shared
`~/.dash` store, projects `.hutch/devkit` into the project, and resolves any
required native compiler under `~/.dash/toolchains`. `dev`, `run`, and `build`
refresh that preparation automatically; `hutch electrobun sync` does the same
work without building.

A typical project looks like this:

```text
my-app/
|-- src/
|   |-- bun/
|   |   `-- index.ts        # Cottontail main process
|   `-- mainview/
|       |-- index.html
|       |-- index.css
|       `-- index.ts
|-- electrobun.config.ts
|-- hutch.config.ts
|-- package.json
|-- package-lock.json
`-- tsconfig.json
```

The split under `src/` mirrors how the app actually runs. `src/bun/index.ts`
is the **main process** — it runs on Cottontail, owns windows and native
state, and is where the privileged side of your app lives. `src/mainview/` is
the **webview UI** — ordinary HTML, CSS, and TypeScript rendered in a native
webview. `electrobun.config.ts` tells Hutch how to put the two together into
an app bundle.

## Build a release

When you're ready to share it:

```bash
hutch electrobun build --env=canary
hutch electrobun build --env=production
```

This produces a signed, distributable build — installer, self-extracting
wrapper, and update metadata included. Canary and production are independent
channels, so you can ship prerelease builds to testers without touching your
production line.

Hutch builds for the operating system and architecture it's running on, so a
complete cross-platform release means running the build on native CI runners
for each target.

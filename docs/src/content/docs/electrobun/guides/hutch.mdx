Hutch is the one CLI you use for everything in Electrobun 2.x. It installs
packages, runs project scripts, bundles TypeScript, downloads pinned
toolchains and Electrobun platform artifacts, and packages applications for
distribution. Where a 1.x workflow juggled Bun, npm, and a separate
Electrobun CLI, 2.x is just `hutch`.

Hutch is build-time tooling — it's what *you* run. Cottontail is the runtime
that ships inside your app; Hutch selects it whenever JavaScript execution is
needed and otherwise stays out of the finished bundle.

## Install Hutch

Install the current production channel on macOS or Linux:

```bash
curl -fsSL https://hutch.blackboard.sh/hutch/install.sh | sh
```

Want to try prerelease builds without touching your daily setup? Install the
canary channel alongside it as `hutch-canary`:

```bash
curl -fsSL https://hutch.blackboard.sh/hutch/install.sh |
  sh -s -- --channel canary
```

On Windows PowerShell:

```powershell
& ([scriptblock]::Create((irm https://hutch.blackboard.sh/hutch/install.ps1)))
```

Pass `-Channel canary` to install `hutch-canary.exe`. The installers also
accept an exact semantic version or build revision. Production and canary
live side by side under `~/.dash/products`, with launchers in `~/.dash/bin`.
`stable` is accepted as an alias for the production channel.

Coming from npm or Bun? `npx electrobun init` and `bunx electrobun init` both
work: the published package installs Hutch when necessary and hands off to
the same native initializer. Prerelease Electrobun packages select Hutch's
canary channel; production packages select production. This bootstrap is
deliberately limited to `init` — day-to-day development and build commands
run through Hutch directly.

## Everyday commands

```bash
# Choose a template, edit the suggested project name, and create the project
hutch electrobun init

# The package-runner spelling is a direct alias
hutch x electrobun init

# Install dependencies and maintain bun.lock
hutch install

# Run hutch.config.ts or package.json scripts
hutch run dev

# Build and launch an Electrobun app
hutch electrobun dev --watch

# Execute a package binary, like npx or bunx
hutch x --package=typescript tsc --version

# Create distributable builds
hutch electrobun build --env=canary
hutch electrobun build --env=production
```

Hutch's build environments are `dev`, `canary`, and `production`.
`--env=stable` remains an alias for `--env=production`.

Scripts resolve in a predictable order: `hutch run <name>` checks the nearest
`hutch.config.ts` first, then falls back to `package.json` scripts
(`dash.config.ts` remains supported as the legacy config name). When the name
is unambiguous, `hutch <name>` works as shorthand. And since scripts don't
have to live in `package.json`, non-JavaScript projects don't need one at all
— a `hutch.config.ts` is enough:

```ts
// hutch.config.ts
export default {
  scripts: {
    dev: "hutch electrobun dev --watch",
    build: "hutch electrobun build --env=production",
  },
};
```

Its first line can also carry the [version pragma](#pin-a-project) that pins
Hutch and Cottontail per project.

One subtlety worth knowing: an exact package request such as
`hutch x electrobun@2.0.0 init` keeps normal package-runner semantics, but
templates always come from the latest matching production or canary catalog.
Pinning an old npm package does not pin an old starter template.

## Versions and updates

The global launchers track independent production and canary channels. Hutch
engines and Cottontail runtimes are stored side by side, so one project can
pin an older release without replacing your global selection.

```bash
hutch self version
hutch self update
hutch cottontail version
hutch cottontail update
```

Interactive use checks for updates periodically. CI and other non-interactive
invocations never prompt.

## Pin a project

Need a project to build the same way for everyone, regardless of what's
installed globally? Place an optional pragma on the first line of
`hutch.config.ts` (or the legacy `dash.config.ts`):

```ts
// @dash cli=production cottontail=production
```

Selectors may be `production`, `stable`, `canary`, an exact semantic version,
or `build:<full-git-revision>`. `stable` resolves to `production`:

```ts
// @dash cli=0.5.0-canary.9 cottontail=0.2.3
```

The pragma selects versions only for that project. It never rewrites the
globally installed channel.

## Toolchains and caches

For Zig, Rust, Go, and Odin main processes, you don't need to install the
compiler yourself. Hutch first accepts a compatible system compiler at
Electrobun's pinned version; otherwise it downloads that exact toolchain into
`~/.dash/toolchains` and shares it across projects. Electrobun native
platform artifacts are cached under `~/.dash/products/electrobun`.

<Aside type="note">
Hutch is build-time tooling. The resulting application contains its selected
main process and Electrobun runtime files; it does not require the user's
global Hutch installation.
</Aside>

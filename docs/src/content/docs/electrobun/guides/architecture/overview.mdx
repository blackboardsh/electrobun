## Build-time architecture

Hutch is the only build orchestrator. It:

1. Loads `electrobun.config.ts`.
2. Resolves the selected Electrobun release and native platform artifact.
3. Installs project dependencies and bundles TypeScript views.
4. Bundles a Cottontail or Bun main process, or compiles a Zig, Rust, Go, or
   Odin main process.
5. Assembles the platform application bundle.
6. For canary and production builds, creates the self-extracting wrapper,
   compressed update archive, metadata, optional patch, and platform installer.
7. Applies configured code signing and notarization.

Hutch and its compiler toolchains are not shipped inside the finished app.

## Runtime architecture

Every Electrobun application contains:

- a small platform launcher
- the selected main-process runtime or native executable
- Electrobun Core and the platform native wrapper
- bundled application code and view assets
- optional CEF and WGPU libraries
- updater metadata and patch tooling

The main process owns application state and privileged native objects. It opens
windows, views, menus, trays, and GPU surfaces through Electrobun Core. Each
webview is a separate native browsing context and communicates with the main
process through Electrobun's event and RPC bridges. The renderer controls its
exact operating-system process model.

## Main-thread model

Native GUI frameworks require their event loop on the process main thread.
Cottontail and Bun run application JavaScript on a worker while Electrobun Core
owns that main-thread event loop. Native SDKs expose the same arrangement
directly: application code initializes the core, starts its work on another
thread where needed, and enters `runMainThread`.

## Application resources

The exact platform layout differs, but the resource model is consistent:

```text
Resources/
|-- app/
|   |-- bun/             # Bundled JavaScript main process, when selected
|   `-- views/           # Bundled and copied webview assets
`-- version.json         # Installed version and update metadata
```

Use the `views://` URL scheme to load files under `Resources/app/views` without
constructing platform filesystem paths.

On macOS, executables and dynamic libraries live under `Contents/MacOS`, assets
under `Contents/Resources`, and optional frameworks under
`Contents/Frameworks`. Windows and Linux bundles use equivalent `bin` and
`Resources` directories.

## Webview engines

System views are the default:

- macOS: WKWebView
- Windows: WebView2
- Linux: WebKitGTK 4.1

CEF can be bundled when a pinned Chromium engine is more important than
download size. macOS and Windows applications can select the renderer per
view. A Linux process uses its CEF wrapper when CEF is bundled and GTK WebKit
otherwise.

`<electrobun-webview>` creates a separately composited native browser view, not
an iframe. `<electrobun-wgpu>` places a native GPU surface in the same layout.
Electrobun synchronizes their bounds, visibility, masking, and input behavior
with the host document.

## Distribution wrapper

A canary or production release wraps the full runnable app in a small native
self-extractor. The payload is a Zstandard-compressed archive. On first launch,
the wrapper verifies and extracts the application to its managed location, then
starts the inner app.

Hutch emits a DMG on macOS, a Setup ZIP on Windows, and a self-extracting setup
archive on Linux. See
[Bundling and Distribution](/electrobun/guides/bundling-and-distribution/) for
the artifact layout.

## Updates

The installed app compares its local hash with hosted update metadata. It first
tries a binary patch from the installed hash to the current release, verifies
the result, and replaces the bundle. If no valid patch path exists, it downloads
the compressed full archive instead.

Static object storage is sufficient for update hosting. The application decides
when to check, download, install, and relaunch through the
[Updater API](/electrobun/apis/updater/).

## Development output

Dev builds skip distribution artifacts and route main-process, webview, and
native diagnostics to the invoking terminal. System webviews and CEF both
forward browser console output in development mode.
